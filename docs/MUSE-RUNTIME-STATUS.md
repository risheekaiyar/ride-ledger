# Odo Muse runtime — local verification

Updated 3 November 2026. The existing published private site and Android APK do not yet run this feature; the tested implementation is the local web runtime in this repository.

The Odo Route Lab offers Ask Muse with an explicit preview of the question and fields sent to Meta: activity, phone placement, approximate duration/distance, GPS acceptance and median accuracy, and estimated screen-off duration. No precise locations, route samples, timestamps or rider notes are included automatically. The question is sent as written. The local server reads a separate server-side credential from an environment variable, calls only `muse-spark-1.3` via Meta Responses with `store:false`, and does not print keys or payloads. A request quota and token ceiling apply. Its in-memory request quota resets on restart and is not an account-wide dollar cap. Do not expose it to the internet.

On 3 November, the owner's separate Odo key successfully authenticated. The first synthetic request returned incomplete at 1,200 output tokens and was rejected. Setting low reasoning effort and a 4,096 output-token ceiling allowed a complete structured response. The owner authorized up to $5 total for tests. Four synthetic requests and one real commute-summary request followed: comparison, an unsupported lean/pothole question, a prompt-injection question, and one end-to-end UI comparison using synthetic ZIPs, plus the owner's real trip summaries. These tests are limited samples, not a general performance guarantee. Confirm actual account charges/credits in Meta Billing; the application does not enforce a provider-wide hard dollar limit.

The synthetic tests produced appropriate caveats about different phone placements and withheld unvalidated lean, potholes, safety and speed-compliance claims. In the real summary test, the owner approved sending the enumerated fields to Meta. Muse noted that pocket and mount results cannot support a calibrated motorcycle-dynamics comparison, that duration/distance were broadly similar, and that direction/traffic information was missing. It asked for that context on future rides. No exact route, coordinates, raw sensor samples, timestamps or notes were sent.

The runtime accepts one or two ride summaries and does not yet send sensor streams, event windows, direction, contextual notes or recurrence history. Evidence IDs link observations to the supplied trip, and schema/IDs plus numeric-in-prose are checked. Those checks do not establish that every model statement is true: the provider's wording about screen-off events being 'confirmed' was too strong, so the prompt was updated to describe them as estimates. That prompt revision has not been tested with another live request. Use of external tools or a model-driven tool loop is not implemented; the current request passes precomputed evidence directly. A wider evaluation and deterministic numeric rendering remain needed.

Run local tests with `node --test scripts/analysis.test.cjs scripts/muse-runtime.test.cjs`. To run a local preview, configure `ODO_META_API_KEY` securely in the process environment and set `ODO_META_MAX_REQUESTS` to a small positive integer, then run `node scripts/serve.cjs`. Never place keys in source, APK, browser JavaScript, command output or commits. The endpoint only binds loopback, checks Host/Origin on writes, limits input length, requires a configured quota and makes no automatic retries. Do not copy credentials from another project.

For hosted operation, migrate the static Site to a server-capable deployment while preserving owner-only access. Store the key as a server secret. Implement a persistent atomic request/spend reservation that cannot reset when workers restart, and verify authentication and consent. The current local in-memory cap is not sufficient for hosted spending control. Android's embedded dashboard also cannot call this local PC runtime; it needs a separately secured reachable service and on-device validation. Do not describe those platforms as connected until tested.
